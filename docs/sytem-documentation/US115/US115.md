# US115a - Create Maintenance Template

## 1. Requirements Engineering

### 1.1. User Story Description

As a Maintenance Technician, I want to create maintenance templates with details including template name, template type (inspection, scheduled maintenance, overhaul, modification), applicable aircraft models, and checklist.

### 1.2. Customer Specifications and Clarifications

- **Clarification from Forum (Conversation 016):** The maintenance intervals (flight hours and calendar days) must be attributes of the Maintenance Template. The system will look at these limits to automatically send an alert to the team every time an aircraft reaches them.

### 1.3. Acceptance Criteria

- **AC1:** The template must include valid maintenance intervals (flight hours and/or calendar days).
- **AC2:** The template type must be one of the specified categories (inspection, scheduled maintenance, overhaul, modification).
- **AC3:** The system must verify that the applicable Aircraft Models exist.
- **AC4:** Only authenticated users with the 'Maintenance Technician' role can perform this operation.
- **AC5:** The API endpoint must follow RESTful principles, returning "201 Created" on success.

### 1.4. Found out Dependencies

- **Dependency to WP#1A (Aircraft Management):** This US depends on the existence of Aircraft Models (US101), as the template needs to be linked to the models it applies to.

### 1.5 Input and Output Data

**Input Data:**
- JSON payload (`CreateTemplateInputDto`):
    - `templateName`
    - `templateType`
    - `flightHoursInterval`
    - `calendarDaysInterval`
    - `checklist` (list of tasks)
    - `applicableAircraftModels` (List of model designations)

**Output Data:**
- "201 Created" HTTP Status.
- `Location` Header with the URL of the newly created resource.
- JSON representation of the created Maintenance Template (`TemplateOutputDto`).

## 3. Design - User Story Realization

### 3.1. Rationale

| Interaction ID | Question: Which class is responsible for... | Answer | Justification (with patterns) |
|:---|:---|:---|:---|
| Step 1 | ...receiving the HTTP POST request? | `MaintenanceTemplateController` | **Controller:** Acts as the API entry point. |

## 5. Construction (Implementation)

The implementation for this User Story follows the same architectural pattern as the others. A `CreateMaintenanceTemplateUseCase` service was created to handle the business logic of creating a `MaintenanceTemplate`. This service receives a DTO from the `MaintenanceTemplateController`, validates the data (e.g., ensuring intervals are non-negative), creates the necessary Value Objects (`MaintenanceInterval`), and instantiates the `MaintenanceTemplate` aggregate root. The new entity is then persisted via the `MaintenanceTemplateRepository`. The controller returns a `201 Created` status, providing the location of the new resource in the `Location` header.

## 6. Integration and Demo

To demonstrate this User Story, one can perform a POST request to `/api/maintenance-templates`.

**Example Request:**
`POST http://localhost:8080/api/maintenance-templates`
Body:
```json
{
    "templateName": "A-Check",
    "templateType": "INSPECTION",
    "flightHoursInterval": 400,
    "calendarDaysInterval": 90,
    "checklist": ["Check tire pressure", "Inspect landing gear"],
    "applicableAircraftModels": ["A320", "A321"]
}
```

**Expected Success Response (201 Created):**
- **Status:** `201 Created`
- **Header:** `Location: http://localhost:8080/api/maintenance-templates/1`
- **Body:** The JSON representation of the newly created template.

## 7. Observations

This User Story is foundational, as maintenance records (US115b) depend on these templates. The use of Value Objects like `MaintenanceInterval` ensures that the domain model is robust and that business rules are enforced at the point of creation. The `@Version` annotation on the `MaintenanceTemplate` entity also provides optimistic locking capabilities, consistent with the project's concurrency requirements.
