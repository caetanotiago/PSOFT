# US115a - Create Maintenance Record

## 1. Requirements Engineering

### 1.1. User Story Description

As a Maintenance Technician, I want to create a maintenance record for a specific aircraft, based on a maintenance template, specifying the start date, expected duration, and the component category.

### 1.2. Customer Specifications and Clarifications

- **Clarification from Forum:** The system must ensure that the aircraft being maintained is registered in the system and that the referenced maintenance template exists.

### 1.3. Acceptance Criteria

- **AC1:** The maintenance record must reference a valid Aircraft (by registration number).
- **AC2:** The maintenance record must reference a valid Maintenance Template.
- **AC3:** The record details must include a description, a valid start date, and an expected duration in minutes.
- **AC4:** Only authenticated users with the 'Maintenance Technician' role can perform this operation.
- **AC5:** The system must prevent concurrent modifications to the same record (Optimistic Locking), which is handled by the `@Version` field on creation.

### 1.4. Found out Dependencies

- **Dependency to WP#1A (Aircraft Management):** Depends on the existence of the specific Aircraft instance (US102) to link the record to the physical airplane.
- **Dependency to US115a:** Depends on the existence of Maintenance Templates.

### 1.5 Input and Output Data

**Input Data:**
- JSON payload (`CreateMaintenanceRecordInputDto`):
    - `aircraftRegistration`
    - `maintenanceTemplateId`
    - `description`
    - `startDate`
    - `expectedDurationMinutes`
    - `componentCategory`

**Output Data:**
- "201 Created" HTTP Status.
- `Location` Header with the URL of the newly created resource.
- JSON representation of the created Maintenance Record (`MaintenanceRecordOutputDto`).

## 3. Design - User Story Realization

### 3.1. Rationale

| Interaction ID | Question: Which class is responsible for... | Answer | Justification (with patterns) |
|:---|:---|:---|:---|
| Step 1 | ...receiving the HTTP POST request? | `MaintenanceController` | **Controller:** Acts as the API entry point. |
| Step 2 | ...coordinating the record creation logic? | `CreateMaintenanceRecordUseCase` | **Application Service (Use Case):** Orchestrates domain objects to fulfill the use case. |
| Step 3 | ...validating dependencies (Aircraft, Template)? | `CreateMaintenanceRecordUseCase` | **Service:** Before creating the record, it should check if the referenced entities exist (using their respective repositories). |
| Step 4 | ...instantiating the new Record and its Value Objects? | `CreateMaintenanceRecordUseCase` | **Creator:** The service acts as a factory for the new aggregate root, creating the Value Objects (`RecordDetails`, `MaintenanceComponent`) and then the `MaintenanceRecord` entity itself. |
| Step 5 | ...saving the new record? | `MaintenanceRecordRepository` | **Repository:** Persists the newly created aggregate root. |
| Step 6 | ...returning the response? | `MaintenanceController` | **Controller:** Formats the DTO, sets the Location header, and sends the 201 Created response. |

- `CreateMaintenanceRecordUseCase` (Application Service)

## 5. Construction (Implementation)

The implementation was centered around the `CreateMaintenanceRecordUseCase` service. This service receives a DTO from the controller, validates the input, creates the `RecordDetails` and `MaintenanceComponent` Value Objects, and then instantiates the `MaintenanceRecord` aggregate root. The new entity is then persisted using the `MaintenanceRecordRepository`. The `MaintenanceController` handles the HTTP POST request and returns a `201 Created` status with a `Location` header pointing to the newly created resource, following REST best practices.

## 6. Integration and Demo

To demonstrate this User Story, one can perform a POST request to `/api/maintenance-records`.

**Example Request:**
`POST http://localhost:8080/api/maintenance-records`
Body:
```json
{
    "aircraftRegistration": "CS-TWB",
    "maintenanceTemplateId": 1,
    "description": "Annual engine inspection",
    "startDate": "2024-10-20",
    "expectedDurationMinutes": 480,
    "componentCategory": "ENGINE"
}
```

**Expected Success Response (201 Created):**
- **Status:** `201 Created`
- **Header:** `Location: http://localhost:8080/api/maintenance-records/5` (assuming 5 is the new ID)
- **Body:** The JSON representation of the newly created record.

## 7. Observations

This use case is fundamental for the system as it's the entry point for creating maintenance tasks. The validation within the Value Objects (`RecordDetails`) ensures that no record can be created in an inconsistent state (e.g., with a negative duration). The separation of concerns between the Controller, Use Case, and Repository is clear and follows the project's architectural guidelines.
