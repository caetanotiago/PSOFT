# US119 - Complete a Maintenance Record

## 1. Requirements Engineering

### 1.1. User Story Description

As a Maintenance Technician, I want to update a maintenance record to mark it as completed and add completion notes.

### 1.2. Customer Specifications and Clarifications

- The system must allow a technician to input optional or mandatory remarks (`CompletionNotes`) once a maintenance task is finished.
- Modifying an existing record requires handling concurrent access to prevent two users from overwriting each other's changes simultaneously. This will be handled via Optimistic Locking.

### 1.3. Acceptance Criteria

- **AC1:** The system must verify if the provided maintenance record ID exists.
- **AC2:** The system must allow the addition of completion notes and set the completion date.
- **AC3:** Concurrent updates must be safely handled using Optimistic Locking. The client must provide the entity's version via an `If-Match` header. If the version does not match, the server must reject the request with a `412 Precondition Failed` or similar error.
- **AC4:** Only authenticated users with the 'Maintenance Technician' role can perform this operation.
- **AC5:** The API endpoint must follow RESTful principles, using a `PATCH` request and returning "200 OK" on success.

### 1.4. Found out Dependencies

- **Dependency to US115b (Create Maintenance Record):** A record must be created first before it can be updated and marked as completed.

### 1.5 Input and Output Data

**Input Data:**
- Record ID (via URL Path Variable).
- `If-Match` Header: Contains the version of the entity being updated.
- JSON payload (`CompleteRecordInputDto`):
    - `notes`: String with the completion notes.

**Output Data:**
- HTTP 200 OK Status.
- The updated JSON representation of the Maintenance Record (`MaintenanceRecordOutputDto`) with HATEOAS links.

## 5. Construction (Implementation)

This User Story was implemented using Optimistic Locking, a requirement for handling concurrent updates. The `MaintenanceRecord` entity includes a field annotated with `@Version`, which Hibernate uses to track changes.

The `CompleteMaintenanceRecordUseCase` service requires the client to send the entity's version in the `If-Match` HTTP header. The service first fetches the record from the database and explicitly compares its current version with the one provided by the client. If they don't match, it throws an `OptimisticLockException`, preventing a "lost update". If they do match, it proceeds to update the entity and calls `repository.save()`. At this point, Hibernate generates an `UPDATE` statement that also checks the version in the `WHERE` clause (`... WHERE id=? AND version=?`). If another transaction has modified the record in the meantime, this update will affect zero rows, and Hibernate will throw a final `OptimisticLockException`.

## 6. Integration and Demo

To demonstrate this User Story, one needs a tool like Postman.

**Step 1: Get the current state and version.**
- `GET http://localhost:8080/api/maintenance-records/1`
- The response will contain the record and an `ETag` header with the version (e.g., `ETag: "0"`).

**Step 2: Send the PATCH request with the correct `If-Match` header.**
- `PATCH http://localhost:8080/api/maintenance-records/1/complete`
- Header: `If-Match: "0"`
- Body: `{ "notes": "Replaced the turbine blades." }`
- **Expected Result:** A 200 OK response with the updated record, which now includes `completionNotes`. The new `ETag` header will be `"1"`.

**Simulating a Conflict:**
1. Two users (User A and User B) fetch the same record at version 0.
2. User A sends the PATCH request with `If-Match: "0"` and successfully updates the record to version 1.
3. User B, unaware of the change, sends their PATCH request, also with `If-Match: "0"`.
4. The server will reject User B's request with a `409 Conflict` (or similar), because the version in the database (1) no longer matches the version User B provided (0).

## 7. Observations

The implementation of Optimistic Locking via `@Version` and `If-Match` headers is a standard and robust pattern for building stateful REST APIs. It ensures data integrity without the heavy performance cost of pessimistic locking (database-level locks). The explicit version check in the use case provides a fast failure path before even attempting a database write.
