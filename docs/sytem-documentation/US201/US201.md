# US201 - Update an aircraft model's specifications

## 1. Requirements Engineering

### 1.1. User Story Description

As a Backoffice Operator, I want to update an aircraft model's specifications.

### 1.2. Customer Specifications and Clarifications

- **From the specifications:** The system must allow updating the technical specifications (standard capacity, fuel capacity, maximum range, cruising speed) of an already registered aircraft model.
- **Non-Functional Requirement:** Proper handling of concurrent access (Optimistic Locking) must be implemented to avoid "Lost Updates" when multiple operators attempt to update the same model simultaneously.

### 1.3. Acceptance Criteria

- **AC1:** The model to be updated must exist in the system.
- **AC2:** All new specification values must be mathematically valid (e.g., positive numeric ranges).
- **AC3:** Concurrent updates must be handled properly, returning `409 Conflict` if version mismatch occurs.
- **AC4:** On success, the system returns `200 OK` with the updated aircraft model details.
- **AC5:** The endpoint follows RESTful principles (`PATCH /api/aircraft-models/{designation}/specifications`) and is restricted to users with the `BACKOFFICE_OPERATOR` role.

### 1.4. Found out Dependencies

- **Dependency to US101:** An `AircraftModel` must already be registered in the system before its specifications can be updated.

### 1.5 Input and Output Data

**Input Data:**
- **Path Variable:** Aircraft Model Designation (e.g., "737-800").
- **Header:** `If-Match` containing the entity's current version (required for Optimistic Locking).
- **JSON Body:** New `ModelSpecifications` (standardSeatingCapacity, fuelCapacity, maximumRange, cruisingSpeed).

**Output Data:**
- JSON object containing the updated Aircraft Model representation (including HATEOAS links).
- HTTP Status `200 OK`.

## 3. Design - User Story Realization

### 3.1. Rationale

**The rationale grounds on the SSD interactions and the identified input/output data.**

| Interaction ID | Question: Which class is responsible for... | Answer | Justification (with patterns) |
|:---|:---|:---|:---|
| Step 1 | ...receiving the HTTP PATCH request? | AircraftModelController | **Controller (REST):** Acts as the entry point for the API, handling HTTP requests. |
| Step 2 | ...coordinating the update logic? | UpdateAircraftModelService | **Application Service:** Orchestrates the use case, finding the entity and applying the update. |
| Step 3 | ...finding the model and handling concurrency? | AircraftModelRepository | **Repository:** Fetches the aggregate. JPA automatically handles the `@Version` increment and optimistic locking validation on save. |
| Step 4 | ...validating the new specifications? | ModelSpecifications | **Information Expert:** The Value Object is responsible for validating its own creation rules (e.g., ensuring positive values). |
| Step 5 | ...returning the response? | AircraftModelController | **Controller:** Formats the DTO into a JSON HTTP response (200 OK) with HATEOAS links via the Assembler. |

### Systematization

## 5. Construction (Implementation)

To be completed during implementation. The update operation will map the DTO to a new ModelSpecifications Value Object and apply it to the entity. The @Version field on AircraftModel ensures JPA handles the optimistic locking.

## 6. Integration and Demo

Demonstrated with PATCH /api/aircraft-models/{designation}/specifications with the If-Match header. Returning 200 OK on success or 409 Conflict on version mismatch.

## 7. Observations

Implementing Optimistic Locking ensures data integrity without relying on expensive database-level pessimistic locks, fulfilling the system's non-functional concurrency requirements.
