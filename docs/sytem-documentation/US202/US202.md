# US202 - Register an aircraft model with an optional image or technical diagram

## 1. Requirements Engineering

### 1.1. User Story Description

As a Backoffice Operator, I want to register an aircraft model with an optional image or technical diagram.

### 1.2. Customer Specifications and Clarifications

- **Clarification:** The creation process implemented in Phase 1 (US101) must be expanded. The system now needs to accept an optional file or link representing the model's image/diagram.
- **Assumption:** The image data can be stored as a Base64 string or a URL reference, encapsulated inside a dedicated Value Object to protect the domain.

### 1.3. Acceptance Criteria

- **AC1:** The system must accept an optional image parameter during the aircraft model creation.
- **AC2:** If no image is provided, the aircraft model must still be created successfully.
- **AC3:** On success, the system returns `201 Created` with the model details, including the image reference if provided.
- **AC4:** The endpoint follows RESTful principles (`POST /api/aircraft-models`) and is restricted to users with the `BACKOFFICE_OPERATOR` role.

### 1.4. Found out Dependencies

- **Dependency to US101:** This US is a direct expansion of the existing model creation endpoint, reusing its core business rules (like manufacturer validation).

### 1.5 Input and Output Data

**Input Data:**
- **JSON Body:** Manufacturer, modelName, specifications (capacity, fuel, range, speed), and an optional `image` field (Base64 string or URL).

**Output Data:**
- JSON object containing the newly created Aircraft Model representation (including HATEOAS links).
- HTTP Status `201 Created`.

## 3. Design - User Story Realization

### 3.1. Rationale

| Interaction ID | Question: Which class is responsible for... | Answer | Justification (with patterns) |
|:---|:---|:---|:---|
| Step 1 | ...receiving the POST request with the image? | AircraftModelController | **Controller (REST):** Handles incoming HTTP requests. |
| Step 2 | ...coordinating the creation process? | CreateAircraftModelService | **Application Service:** Orchestrates the use case flow. |
| Step 3 | ...encapsulating and validating the image? | ModelImage | **Value Object:** Wraps the string/URL and guarantees format validity upon instantiation. |
| Step 4 | ...persisting the new model? | AircraftModelRepository | **Repository:** Saves the aggregate securely to the database. |
| Step 5 | ...returning the response? | AircraftModelController | **Controller:** Formats the resulting DTO into a JSON response (201 Created). |

### Systematization

According to the taken rationale, the conceptual classes promoted to software classes are:
- AircraftModel
- ModelImage (Value Object)

Other software classes (i.e. Pure Fabrication) identified:
- AircraftModelController
- CreateAircraftModelService
- AircraftModelRepository
- CreateAircraftModelDTO

## 7. Observations

Handling the image reference as a Domain Value Object maintains the system's separation of concerns, decoupling the pure Domain logic from Cloud Storage or File System infrastructures.
