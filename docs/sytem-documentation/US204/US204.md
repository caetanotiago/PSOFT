# US204 - View the Top 5 most utilized aircraft models

## 1. Requirements Engineering

### 1.1. User Story Description

As a Backoffice Operator, I want to see the Top 5 most utilized aircraft models based on total flight hours or number of assignments.

### 1.2. Customer Specifications and Clarifications

- **Clarification:** The utilization can be measured by two distinct metrics: either by the sum of flight hours accumulated by all aircraft belonging to that model, or by the total number of flight assignments those aircraft have completed.
- **Business Rule:** The system must aggregate the data dynamically and return a maximum of 5 records, ordered descending by the selected metric.
- **Non-Functional Requirement:** Performance must be ensured. Aggregations on large datasets must be optimized.

### 1.3. Acceptance Criteria

- **AC1:** The system must allow the user to select the metric ("flight_hours" or "assignments") via request parameters.
- **AC2:** The result must contain at most 5 elements, ordered descending.
- **AC3:** If there are no flights registered, the system should return an empty list with `200 OK`.
- **AC4:** The endpoint follows RESTful principles (`GET /api/aircraft-models/top-utilized`) and is restricted to users with the `BACKOFFICE_OPERATOR` role.

### 1.4. Found out Dependencies

- **Dependency to US101:** Requires `AircraftModel` entities to exist in the catalog.
- **Dependency to WP#3B:** Requires scheduled flights or flight histories to exist in order to calculate the actual utilization of the aircraft.

### 1.5 Input and Output Data

**Input Data:**
- **Query Parameter:** `metric` (e.g., `?metric=flight_hours` or `?metric=assignments`).

**Output Data:**
- JSON array containing up to 5 `AircraftModelUtilizationDTO` objects (each detailing the model designation and its respective accumulated metric value).
- HTTP Status `200 OK`.

## 3. Design - User Story Realization

### 3.1. Rationale

| Interaction ID | Question: Which class is responsible for... | Answer | Justification (with patterns) |
|:---|:---|:---|:---|
| Step 1 | ...receiving the HTTP GET request? | AircraftModelController | **Controller (REST):** Entry point for model-related endpoints. |
| Step 2 | ...coordinating the report generation? | ViewTopUtilizedModelsService | **Application Service:** Orchestrates the use case and metric evaluation. |
| Step 3 | ...calculating the sum/count and ordering? | AircraftModelRepository | **Repository:** Executes an optimized JPQL query to retrieve the aggregated results, using `Pageable` to enforce the LIMIT 5 restriction. |
| Step 4 | ...encapsulating the result? | AircraftModelUtilizationDTO | **DTO:** Transports only the strictly relevant data (model name and metric total) to the web layer without exposing domain entities. |
| Step 5 | ...returning the response? | AircraftModelController | **Controller:** Formats the DTOs into a JSON HTTP response. |

## 5. Construction (Implementation)

To be completed during implementation. The core logic involves a custom JPQL @Query in the repository that uses PageRequest.of(0, 5) to apply the SQL LIMIT 5 natively at the database level.

## 6. Integration and Demo

Demonstrated with GET /api/aircraft-models/top-utilized?metric=flight_hours.

## 7. Observations

Fetching all models and their flights to sort them in Java memory would violate performance NFRs. Passing a Pageable of size 5 to a JPQL query with GROUP BY is the optimal architectural choice.
